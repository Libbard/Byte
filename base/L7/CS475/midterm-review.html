1 مقدمة في الحوسبة المتنقلة والأدوات الأساسية

تغطي هذه الوحدة رؤية السعودية 2030، المكتبة الرقمية السعودية، أنظمة التحكم في الإصدارات (Git و GitHub)، وموقع Stack Overflow.

1.1 رؤية السعودية 2030

خارطة طريق استراتيجية للمملكة تعتمد على مكانتها الإسلامية، قوتها الاستثمارية، وموقعها الجغرافي الاستراتيجي.

أُطلقت رؤية 2030 بقيادة خادم الحرمين الشريفين ورُسمت من قبل سمو ولي العهد لاستغلال إمكانات المملكة.

تعتمد الرؤية على ثلاث نقاط قوة جوهرية:

  1. العمق العربي والإسلامي: المملكة هي أرض الحرمين الشريفين.
  2. القوة الاستثمارية: لخلق اقتصاد متنوع ومستدام.
  3. الموقع الاستراتيجي: لربط ثلاث قارات (أفريقيا، آسيا، وأوروبا) وتكون محركاً للتجارة الدولية.

1.2 المكتبة الرقمية السعودية (SDL)

أكبر تجمع أكاديمي لمصادر المعلومات في العالم العربي، يوفر وصولاً موحداً للمراجع العلمية لجميع الجامعات السعودية.

تحتوي المكتبة على أكثر من 310,000 مرجع علمي وتتعاقد مع أكثر من 300 ناشر عالمي.

فازت بجائزة الاتحاد العربي للمكتبات والمعلومات في عام 2010. من أهم مزاياها:

  1. إدارة مركزية لمحتوى ضخم ومُحدّث باستمرار.
  2. مشاركة المنفعة بين جميع الجامعات في أي مجال علمي.
  3. تعزيز مكانة الجامعات في الاعتماد الأكاديمي.
  4. سد الفجوة بين الجامعات الناشئة والجامعات الكبرى من خلال توفير نفس الخدمات للجميع.

1.3 التحكم في الإصدارات ونظام Git

نظام يسجل التغييرات على الملفات بمرور الوقت لتتمكن من استرجاعها لاحقاً، ويعتبر Git أشهر برامج هذا النظام.

التحكم في الإصدارات (VCS): يسمح لك بإرجاع الملفات أو المشروع بأكمله إلى حالة سابقة، مقارنة التغييرات، معرفة من قام بالتعديل، واستعادة الملفات المفقودة.

نظام Git: هو برنامج للتحكم في الإصدارات لتتبع التغييرات وتنسيق العمل بين عدة أشخاص.

يُستخدم أساساً لإدارة الكود المصدري. تم إنشاؤه بواسطة لينوس تورفالدس (Linus Torvalds) لتطوير نواة لينكس (Linux Kernel).

1.4 منصة GitHub

شركة ربحية تقدم خدمة استضافة سحابية لمستودعات Git، مما يسهل التعاون بين المطورين.

GitHub ليس هو Git.

Git هو البرنامج نفسه، بينما GitHub هو المكان الذي ترفع عليه مستودع Git الخاص بك.

يوفر GitHub واجهة مستخدم سهلة الاستخدام (User-friendly) تجعل من السهل حتى على المبرمجين المبتدئين الاستفادة من قوة Git في التحكم في الإصدارات والتعاون مع الفرق.

1.5 موقع Stack Overflow

موقع أسئلة وأجوبة للمبرمجين يقبل فقط الأسئلة البرمجية المحددة بدقة ويرفض الأسئلة المبنية على الآراء.

تم إنشاء الموقع في عام 2008 بواسطة جيف أتوود (Jeff Atwood) وجويل سبولسكي (Joel Spolsky). وهو الموقع الرئيسي لشبكة Stack Exchange.

يتميز الموقع بقواعد صارمة: يقبل فقط الأسئلة المتعلقة بالبرمجة والتي تركز على مشكلة محددة.

الأسئلة ذات الطبيعة الواسعة أو التي تدعو إلى إجابات تعتمد على الرأي يتم رفضها وإغلاقها من قبل مستخدمي الموقع.

2 بداية الأندرويد والجافا: الاتصال الأول مع جافا، XML، ومصمم واجهة المستخدم

مقدمة شاملة لتطوير تطبيقات الأندرويد باستخدام لغة جافا، تشمل إعداد بيئة العمل Android Studio، فهم هيكلية التطبيق (Java و XML)، والتعامل مع واجهة المستخدم والرسائل النصية.

2.1 لغة جافا ونظام أندرويد

جافا هي لغة البرمجة الأساسية لتطوير تطبيقات الأندرويد، وتوفر مكتبات ضخمة تسهل بناء التطبيقات.

تُستخدم لغة جافا بشكل واسع في تطوير تطبيقات الأندرويد لأنها لغة كائنية التوجه (Object-Oriented) تمتلك مجموعة واسعة من المكتبات.

تتضمن حزمة تطوير الأندرويد (Android SDK) العديد من مكتبات جافا القياسية التي توفر وظائف جاهزة لهياكل البيانات، الدوال الرياضية، الرسوميات، والشبكات.

تساعد جافا في إنشاء وتحسين التطبيقات بسرعة وكفاءة، كما تسهل تنفيذ وإصلاح المشاكل الشائعة مقارنة بلغات البرمجة الأخرى.

2.2 بيئة تشغيل أندرويد (ART)

نظام ART هو المحرك الذي يحول كود جافا المترجم (Bytecode) إلى لغة الآلة (Machine code) عند تثبيت التطبيق على الجهاز.

تعمل لغة جافا ونظام أندرويد معًا من خلال عملية متعددة المراحل.

  1. أولاً، يتم تحويل كود جافا الذي يكتبه المطور إلى كود وسيط يُعرف بـ Bytecode بعد عملية الترجمة (Compilation).
  2. ثانيًا، يقوم نظام Android Runtime (ART) بتحويل هذا الـ Bytecode إلى كود آلة (Machine code) مخصص للجهاز، وذلك عند تثبيت التطبيق وليس عند تشغيله.

هذا النهج يجعل البرمجة سريعة للمطور، والتشغيل سريعًا وفعالًا للجهاز.

2.3 واجهة برمجة تطبيقات أندرويد ونظام التشغيل

واجهة برمجة التطبيقات (API) هي وسيط برمجي يسمح لتطبيقك بالتحدث مع نظام تشغيل أندرويد المبني على نواة لينكس.

تُستخدم Android framework API من قِبل التطبيقات للتفاعل مع نظام أندرويد الأساسي.

واجهة برمجة التطبيقات هي عبارة عن مجموعة من أكواد جافا المكتوبة مسبقًا والجاهزة للاستخدام (Plug and play). تعمل كرسول ينقل الطلبات إلى مزود الخدمة ويعيد الاستجابة.

نظام أندرويد نفسه هو نظام تشغيل مبني على Linux، وهو يتعامل مع النطاق المعقد والمتنوع للغاية من الأجهزة (مثل المعالج، الذاكرة، و GPS) من خلال برامج تشغيل (Drivers) يوفرها مصنعو الأجهزة.

2.4 إعداد بيئة Android Studio

أندرويد ستوديو هو بيئة التطوير المتكاملة (IDE) الرسمية، ويتطلب حزمة تطوير جافا (JDK) وحزمة تطوير أندرويد (SDK) للعمل.

Android Studio هو بيئة التطوير المتكاملة الرسمية لتطوير تطبيقات أندرويد. يتكون من مكونين رئيسيين:

  • JDK (Java Development Kit): ضروري لاستخدام وكتابة كود جافا.
  • Android SDK: مجموعة من الأدوات وواجهات برمجة التطبيقات (API) الخاصة بتطوير أندرويد.

تشمل مهام Android Studio توفير واجهة التطوير، ترجمة الكود (Compiling)، وربط الكود مع JDK و Android API.

2.5 هيكلية التطبيق: جافا و XML

يُكتب منطق التطبيق بلغة جافا (في ملف MainActivity.java)، بينما تُصمم واجهة المستخدم باستخدام لغة XML (في ملف fragment_first.xml).

يتكون مشروع الأندرويد الأساسي من ملفات برمجية وملفات تصميم:

  1. ملف MainActivity.java: يحتوي على منطق التطبيق. يبدأ بتعريف الحزمة (Package declaration)، ثم استيراد الفئات المطلوبة (Importing classes)، ثم تعريف الفئة الأساسية (Class declaration) التي ترث من `AppCompatActivity`.
  2. دالة onCreate(): هي الدالة الأساسية التي تُستدعى تلقائيًا قبل بدء تشغيل التطبيق مباشرة، وفيها يوضع الكود المبدئي.
  3. ملف fragment_first.xml: يوجد في مجلد `res/layout` ويحتوي على كود XML الذي يشكل واجهة المستخدم. يمكن تعديله عبر واجهة التصميم المرئية (Design view) أو عبر كتابة الكود (Code view).

2.6 برمجة الرسائل: Log و Toast

تُستخدم فئة Log لإرسال رسائل للمطورين في نافذة Logcat، بينما تُستخدم فئة Toast لعرض رسائل منبثقة للمستخدمين على الشاشة.

يوفر Android API فئتين مختلفتين لإخراج الرسائل النصية:

  1. Log: يسمح بإخراج رسائل تتبع ومعلومات إلى نافذة Logcat في Android Studio. هذه الرسائل مخفية عن المستخدم النهائي وتُستخدم لأغراض التصحيح (Debugging).
  2. Toast: ينتج رسالة منبثقة صغيرة تظهر على شاشة جهاز المستخدم لفترة قصيرة ثم تختفي. تُستخدم لإعطاء تغذية راجعة سريعة للمستخدم.

3 استكشاف أندرويد ستوديو وهيكل المشروع

تغطي هذه الوحدة هيكل مشروع أندرويد، والفرق بين قوالب Empty Activity و Basic Activity، بالإضافة إلى كيفية استخدام محاكي أندرويد.

3.1 قوالب المشروع وتشريحه

القالب (Template) هو نقطة البداية التي تحدد الملفات والمحتويات الدقيقة التي سيقوم أندرويد ستوديو بإنشائها تلقائياً.

عند إنشاء مشروع أندرويد جديد، يتم استخدام قالب لتحديد الملفات الأساسية.

قالب Empty Activity هو أبسط نوع من المشاريع ويحتوي على واجهة مستخدم (UI) مُنشأة تلقائياً.

يقوم أندرويد ستوديو بإنشاء كود Java اللازم لعرض هذه الواجهة، وعند إضافته إلى واجهة المستخدم الفارغة، يصبح التطبيق جاهزاً للعرض.

3.2 هيكل مجلدات Empty Activity

يتكون المشروع الأساسي من أربعة مجلدات رئيسية: manifests، java، java (generated)، و res.

عند توسيع مجلد app في مستكشف المشروع، نجد المجلدات التالية:

  • manifests — يحتوي على ملف AndroidManifest.xml.
  • java — يحتوي مبدئياً على ملف واحد وثلاثة مجلدات، ويمتلئ بالملفات مع تطور المشروع.
  • java (generated) — يحتوي على كود يتم إنشاؤه تلقائياً بواسطة أندرويد ستوديو.
  • res — يحتوي على جميع الموارد غير البرمجية.

3.3 مجلد الموارد (res)

مجلد res يحتوي على جميع الموارد غير البرمجية للتطبيق مثل الصور، التخطيطات (Layouts)، الأيقونات، والنصوص.

ينقسم مجلد res إلى عدة مجلدات فرعية رئيسية:

  • drawable — يحتوي على ملفات الرسومات (مثل ic_launcher_foreground و ic_launcher_background).
  • layout — يحتوي على ملفات XML التي تحدد واجهة المستخدم.
  • mipmap — مخصص لأيقونات مشغل التطبيق (Launcher icons)، ويحتوي على مجلدات فرعية للأيقونات العادية والدائرية.
  • values — يحتوي على ملفات XML للقيم البسيطة مثل colors.xml (للألوان)، strings.xml (للنصوص واسم التطبيق)، و styles.xml (للسمات/Themes).

3.4 قالب Basic Activity

قالب Basic Activity هو خطوة متقدمة عن Empty Activity، حيث يضيف شريط أدوات (Toolbar) وزر إجراء عائم (Floating Action Bar).

عند استكشاف مشروع Basic Activity، نلاحظ التالي:

  • MainActivity.java — يشير الكود إلى موردين رئيسيين: R.id.toolbar و R.id.fab.
  • activity_main.xml — يقوم بإعداد شريط الأدوات وزر الإجراء العائم ليكونا جاهزين للاستخدام.
  • القوائم (Menus) — يحتوي ملف Java على دالة إضافية onCreateOptionsMenu يتم استدعاؤها بواسطة نظام التشغيل مباشرة لتعزيز القائمة المعرفة في ملف menu_main.xml.

3.5 محاكي أندرويد (Android Emulator)

المحاكي هو جهاز افتراضي يمكنه محاكاة كل ميزات الهاتف الحقيقي لاختبار التطبيقات.

يحتوي المحاكي على لوحة تحكم مصغرة (Control Panel) توفر عدة أدوات:

  1. عناصر تحكم النافذة — لتصغير أو إغلاق نافذة المحاكي.
  2. الطاقة والصوت — لإيقاف تشغيل المحاكي (محاكاة إغلاق الجهاز الفعلي) وزيادة/خفض الصوت.
  3. التدوير — زران لتدوير المحاكي يميناً ويساراً لمعاينة التطبيق في اتجاهات مختلفة.
  4. أزرار التنقل — أيقونات تحاكي زر الرجوع، زر الشاشة الرئيسية، وعرض التطبيقات النشطة.
  5. الإعدادات المتقدمة (Advanced Settings) — للتفاعل مع الأجهزة مثل المستشعرات، نظام تحديد المواقع (GPS)، البطارية، وقارئ البصمة.

4 البدء مع التخطيطات والتصميم الجميل باستخدام CardView و ScrollView

مقدمة لتصميم واجهة المستخدم في أندرويد، مبادئ Material Design، أنواع التخطيطات (LinearLayout، ConstraintLayout، TableLayout)، وخصائص الواجهة، بالإضافة إلى استخدام ScrollView و CardView.

4.1 التصميم المادي (Material Design)

مجموعة من المبادئ والقواعد لإنشاء واجهات مستخدم جذابة ومتسقة تعتمد على مفهوم طبقات المواد.

الهدف الأساسي من التصميم المادي هو تبسيط عملية إنشاء واجهات مستخدم جذابة. وهو مستمد مباشرة من مبادئ التصميم الأساسية.

يستخدم التصميم المادي مفهوم طبقات المواد (layers of materials)، وهو مشابه لما يوجد في تطبيقات تحرير الصور، لإنشاء عمق وتسلسل هرمي بصري.

يوفر مجموعة من المبادئ والقواعد والإرشادات التي تضمن الاتساق (consistency) عبر التطبيق.

4.2 تصميم واجهة أندرويد الحساس للسياق

تصميم واجهة أندرويد حساس للسياق، حيث يعتمد تأثير خصائص العنصر على التخطيط الأب أو العناصر المجاورة.

تصميم واجهة المستخدم في أندرويد حساس للسياق (context-sensitive). الطريقة التي تؤثر بها خاصية معينة (مثل x) لعنصر واجهة (widget) على مظهره قد تعتمد على خاصية أخرى (مثل y) أو حتى على خاصية في عنصر آخر.

عند سحب وإفلات العناصر في المصمم، يختلف كود XML (Extensible Markup Language) الذي يتم إنشاؤه بشكل كبير بناءً على نوع التخطيط (Layout) المستخدم.

تستخدم أنواع التخطيطات المختلفة تقنيات مختلفة لتحديد موضع العنصر؛ على سبيل المثال، يختلف LinearLayout تماماً عن ConstraintLayout.

4.3 التخطيط الخطي (LinearLayout)

أبسط أنواع التخطيطات، يقوم بترتيب العناصر داخله بشكل خطي إما عمودياً أو أفقياً.

يُعد LinearLayout أبسط أنواع التخطيطات في أندرويد. يتم ترتيب جميع عناصر واجهة المستخدم (UI items) داخله بشكل خطي.

هناك خياران فقط لاتجاه الترتيب (Orientation):

  • عمودي (Vertical) — ترتيب العناصر من الأعلى إلى الأسفل.
  • أفقي (Horizontal) — ترتيب العناصر من اليسار إلى اليمين (أو العكس حسب اللغة).

4.4 تخطيط القيود (ConstraintLayout)

تخطيط متقدم يسمح ببناء واجهات دقيقة ومعقدة عن طريق ربط العناصر ببعضها أو بحواف الشاشة باستخدام القيود.

يُستخدم ConstraintLayout لبناء واجهة مستخدم دقيقة. يتم إنشاؤه تلقائياً كالتخطيط الافتراضي عند إنشاء مشروع جديد في Android Studio.

يمكن إضافة القيود (Constraints) يدوياً عن طريق تحديد العنصر وسحب الدوائر الصغيرة الموجودة في الأعلى، الأسفل، اليسار، واليمين لربطها بعناصر أخرى أو بحواف الشاشة.

تساعد نافذة Component Tree (شجرة المكونات) في تصور هيكل التخطيط لملف XML بدون عرض كل التفاصيل المعقدة.

4.5 تخطيط الجدول (TableLayout)

تخطيط يشبه جدول البيانات (Spreadsheet)، يعرض العناصر في صفوف وأعمدة محاذاة بدقة باستخدام TableRow.

يُستخدم TableLayout لبناء تخطيط يشبه جدول البيانات مع خلايا محاذاة بدقة تحتوي على عناوين وبيانات.

لبناء الجدول، يتم إضافة عناصر TableRow داخل الـ TableLayout. كل TableRow يمثل صفاً، والعناصر التي توضع داخله تمثل الأعمدة.

يمكن التحكم في موضع العنصر داخل الصف باستخدام خاصية layout_column (مثلاً تعيينها إلى 1 لوضع العنصر في العمود الأوسط إذا كان الفهرس يبدأ من 0).

4.6 خصائص الواجهة: الحجم والمسافات (UI Attributes)

خصائص تحدد أبعاد العناصر (dp, sp)، سلوكها مع المحتوى (wrap/match)، والمسافات الداخلية (padding) والخارجية (margin).

تتضمن الخصائص الأساسية لتصميم الواجهة ما يلي:

  1. dp (Density-independent pixels) — وحدة قياس مستقلة عن كثافة الشاشة، تُستخدم لتحديد أحجام العناصر لضمان تناسقها عبر الأجهزة المختلفة.
  2. sp (Scalable pixels) — وحدة قياس تعتمد على الجهاز، تُستخدم لتحديد أحجام الخطوط (Fonts) لأنها تتأثر بإعدادات حجم الخط الخاصة بالمستخدم.
  3. wrap_content — يجعل حجم العنصر يتقلص ليحتوي محتواه فقط.
  4. match_parent — يجعل العنصر يتمدد ليملأ المساحة المتاحة في العنصر الأب.
  5. Padding — المسافة من حافة العنصر إلى بداية المحتوى داخله (مسافة داخلية).
  6. Margin — المسافة خارج العنصر التي تفصله عن العناصر الأخرى (مسافة خارجية).

4.7 الوزن والجاذبية (layout_weight & Gravity)

layout_weight يقسم المساحة المتاحة بين العناصر بنسب معينة، بينما Gravity تتحكم في محاذاة المحتوى داخل العنصر.

خاصية layout_weight:

  • تُستخدم لتقسيم مساحة الشاشة بين أجزاء واجهة المستخدم.
  • تحافظ على التناسق في المساحة النسبية التي تشغلها العناصر بغض النظر عن حجم شاشة الجهاز.
  • تُستخدم غالباً مع تعيين العرض أو الارتفاع إلى 0dp.

الجاذبية (Gravity):

  • تؤثر على موضع العناصر عن طريق تحريكها في اتجاه معين.
  • android:gravity — تتحكم في محاذاة المحتوى داخل العنصر (مثلاً: left|center_vertical).
  • android:layout_gravity — تتحكم في محاذاة العنصر نفسه بالنسبة للتخطيط الأب.

4.8 التمرير والبطاقات (ScrollView & CardView)

ScrollView يسمح للمستخدم بتمرير المحتوى عندما يتجاوز حجم الشاشة، بينما CardView يعرض المحتوى داخل بطاقات أنيقة.

ScrollView:

  • يسمح للمستخدم بالتمرير (scroll) عبر المحتوى عن طريق السحب بإصبعه عندما يكون هناك محتوى كبير لا يتسع للشاشة.
  • يتم استخدامه كعنصر جذر (Root element) بدلاً من ConstraintLayout في بعض الحالات.

CardView:

  • يُستخدم لتصميم واجهات جميلة حيث يتم تجميع المحتوى (مثل الصور والنصوص) داخل بطاقات.
  • يمكن إضافة الصور إلى المشروع عن طريق نسخها إلى مجلد res/drawable.
  • يتم تعريف أبعاد البطاقات (مثل الزوايا الدائرية والظلال) في ملف dimens.xml داخل مجلد values.

5 دورة حياة نظام أندرويد

مقدمة شاملة لدورة حياة تطبيقات أندرويد، بما في ذلك الحالات المختلفة للنشاط (Activity)، ودوال الاستدعاء (Callbacks)، وكيفية إدارة الموارد وحفظ البيانات أثناء انتقال التطبيق بين الحالات المختلفة.

5.1 مراحل دورة حياة أندرويد

هي الطريقة التي تتفاعل بها جميع تطبيقات أندرويد مع نظام التشغيل، حيث يمر التطبيق بمراحل متميزة من الإنشاء إلى التدمير. تخيلها كدورة حياة كائن حي يولد، ينشط، ينام، ثم يموت.

يحتوي نظام أندرويد على مراحل متميزة تحدد كيفية عرض التطبيق للمستخدم، أو ما إذا كان يُعرض على الإطلاق.

بناءً على هذه المراحل، يقوم نظام أندرويد بتخصيص الموارد مثل الذاكرة وقوة المعالجة.

كل تطبيق على جهاز أندرويد سيكون في إحدى المراحل التالية:

  1. قيد الإنشاء (Being created)
  2. البدء (Starting)
  3. الاستئناف (Resuming)
  4. قيد التشغيل (Running)
  5. الإيقاف المؤقت (Pausing)
  6. التوقف (Stopping)
  7. قيد التدمير (Being destroyed)

5.2 فئة النشاط ودوالها

النشاط (Activity) يمثل شاشة واحدة في واجهة مستخدم التطبيق. يتفاعل أندرويد مع التطبيق عن طريق استدعاء دوال محددة داخل هذه الفئة.

يتم تمثيل جميع الأنشطة في تطبيقات أندرويد بواسطة فئة النشاط، وهي فئات فرعية من android.app.Activity.

تحتوي هذه الفئة على مجموعة من الدوال التي ترتبط بحالة دورة حياة النشاط.

  • onCreate: أول دالة تُنفذ عند إنشاء النشاط. تُستخدم لتعريف واجهة المستخدم عبر setContentView.
  • onStart: تُنفذ عندما يكون التطبيق في مرحلة البدء، مما يجعل النشاط مرئياً للمستخدم.
  • onResume: تعمل بعد onStart، وتُستدعى أيضاً بعد إيقاف التطبيق مؤقتاً. تقوم بإعادة تحميل بيانات المستخدم المحفوظة.
  • onPause: تُستدعى عندما يتوقف التطبيق مؤقتاً (مثل انتقال الجهاز لوضع السكون أو التبديل لتطبيق آخر). يجب حفظ البيانات غير المحفوظة هنا.
  • onStop: تتعلق بمرحلة التوقف. تقوم بمهام مثل تحرير موارد النظام.
  • onDestroy: تُستدعى عند تدمير النشاط نهائياً وإزالته من الذاكرة.

5.3 انتقالات حالة التطبيق

تتغير حالة التطبيق بناءً على تفاعل المستخدم، مثل فتح التطبيق، أو التبديل إلى تطبيق آخر، أو إغلاقه. كل إجراء يطلق سلسلة محددة من دوال دورة الحياة.

لفهم كيفية عمل دورة الحياة في العالم الحقيقي، دعونا نأخذ مثال التبديل من تطبيق فيسبوك إلى تطبيق البريد الإلكتروني:

  1. عندما يضغط المستخدم على أيقونة فيسبوك، يتم إنشاء (created) التطبيق وبدؤه (started).
  2. بعد البدء، يدخل التطبيق في مرحلة الاستئناف (resuming).
  3. بمجرد استئناف التطبيق، يصبح له السيطرة الكاملة على الشاشة وحصة أكبر من الذاكرة وقوة المعالجة، ويدخل في مرحلة التشغيل (Running).
  4. عند التبديل من فيسبوك إلى تطبيق البريد الإلكتروني، ينتقل فيسبوك إلى مرحلة الإيقاف المؤقت (paused)، ثم إلى مرحلة التوقف (stopping).
  5. تطبيق البريد الإلكتروني الذي تم التبديل إليه سيمر بمراحل: الإنشاء ← البدء ← الاستئناف ← التشغيل.

5.4 مقدمة عن الأجزاء (Fragments)

الجزء (Fragment) هو فئة تشبه النشاط (Activity) وتعمل كجزء منه، تمثل شاشة أو جزءاً من واجهة المستخدم، ولها دورة حياتها الخاصة.

في قوالب أندرويد الحديثة (مثل Basic Activity Template)، يحتوي المشروع على ملف MainActivity.java بالإضافة إلى ملفات مثل FirstFragment.java و SecondFragment.java.

يحتوي النشاط الرئيسي على الكود اللازم للتعامل مع تنقل المستخدم بين الشاشات المختلفة (الأجزاء).

  • الجزء يمثل شاشة (Screen).
  • يتم التحكم في الأجزاء بواسطة فئات النشاط (Activity classes).
  • يمتلك الجزء دوال دورة حياة خاصة به (مثل onCreateView).

6 نوافذ الحوار والمحولات وإعادة التدوير في أندرويد

تغطي هذه الوحدة كيفية إنشاء نوافذ الحوار (Dialog Windows) باستخدام DialogFragment، بالإضافة إلى حل مشكلات الذاكرة عند عرض قوائم طويلة باستخدام RecyclerView و RecyclerAdapter.

6.1 نافذة الحوار (Dialog Window) و DialogFragment

نافذة منبثقة لعرض الإشعارات أو رسائل التأكيد للمستخدم، تُبنى باستخدام فئة DialogFragment.

نوافذ الحوار في أندرويد هي فئات متطورة تتكون من تخطيطات وعناصر واجهة مستخدم محددة.

لإنشاء نافذة حوار، نقوم بإنشاء فئة جديدة ترث من DialogFragment.

يتم تجاوز الدالة onCreateDialog لتعريف وبناء واجهة الحوار باستخدام AlertDialog.Builder، ويتم استدعاء الدالة getActivity() لتمرير المرجع إلى النشاط الرئيسي (MainActivity).

6.2 التسلسل (Chaining)

عملية استدعاء أكثر من دالة واحدة بتسلسل على نفس الكائن في سطر برمجي واحد.

التسلسل يشبه كتابة أسطر متعددة من التعليمات البرمجية بطريقة موجزة.

يُستخدم بكثرة مع AlertDialog.Builder لتعيين خصائص الحوار.

  1. setMessage(): يحدد الرسالة الرئيسية للمستخدم.
  2. setPositiveButton(): يحدد النص (مثل "OK") والمستمع (Listener) للنقر.

6.3 عرض إعادة التدوير (RecyclerView)

أداة واجهة مستخدم متقدمة تعرض قوائم طويلة بكفاءة عن طريق إعادة تدوير عناصر العرض (Views) بدلاً من إنشاء عناصر جديدة لكل عنصر بيانات.

المشكلة في استخدام ScrollView مع عدد كبير من عناصر TextView هي أن جهاز أندرويد قد تنفد ذاكرته (Out of Memory) بسبب تحميل جميع العناصر في وقت واحد.

الحل هو استخدام RecyclerView.

فهو يحتفظ بعدد محدود من عناصر العرض (فقط ما يظهر على الشاشة) ويعيد استخدامها (Recycle) لعرض بيانات جديدة أثناء التمرير.

6.4 محول إعادة التدوير (RecyclerAdapter)

الفئة المسؤولة عن ربط البيانات (مثل ArrayList) بعناصر واجهة المستخدم داخل RecyclerView.

لإنشاء محول مخصص، يجب أن نرث من RecyclerView.Adapter ونتجاوز ثلاث دوال رئيسية:

  1. onCreateViewHolder: تُستدعى عندما يحتاج RecyclerView إلى تخطيط (Layout) لعنصر جديد في القائمة.
  2. onBindViewHolder: تُستدعى لربط البيانات (من المصفوفة) بعنصر العرض (ViewHolder) في موضع معين.
  3. getItemCount: تُرجع العدد الإجمالي للعناصر في مصفوفة البيانات.

حديث البروفيسور

أهلاً بكم يا أبنائي وبناتي طلاب وطالبات مقرر CS475 في ليلة الاختبار النصفي. الليلة هي ليلة ربط الخيوط وتجميع الصورة الكاملة لكل ما تعلمناه في الوحدات الست الأولى. دعونا نسترجع رحلتنا معاً؛ بدأنا في الوحدة الأولى بفهم السياق التقني الوطني ورؤية المملكة 2030، وتسلحنا بأدوات المطور الأساسية مثل Git و دورة حياة تطوير البرمجيات (SDL)، وهي الأساس الذي تبنى عليه أي بيئة عمل احترافية. ثم انتقلنا في الوحدة الثانية إلى لغة الجافا وتصميم واجهات المستخدم عبر XML، حيث أدركنا كيف تتخاطب لغة البرمجة (المنطق) مع لغة التوصيف (التصميم) لإنشاء تطبيق متكامل. في الوحدة الثالثة، غصنا في أعماق بيئة Android Studio، وتعرفنا على هيكلية المشروع وملفاته، وكيفية استخدام المحاكي لتجربة تطبيقاتنا. بعد أن أرسخنا الأساسيات، انطلقنا في الوحدة الرابعة نحو الإبداع البصري، حيث تعلمنا بناء واجهات جذابة ومتجاوبة باستخدام CardView و ScrollView ومبادئ Material Design. وهنا يأتي الفخ الاختباري الأول: لا تخلطوا بين أنواع التنسيقات (Layouts) المختلفة ومتى نستخدم كل نوع لتحقيق أفضل تجربة للمستخدم. أما الوحدة الخامسة، فهي قلب الأندرويد النابض: "دورة حياة التطبيق" (Android Lifecycle). فهمكم العميق لدوال مثل onCreate و onPause و onDestroy هو مفتاح النجاح، والفخ الأكبر هنا هو نسيان كيفية تعامل النظام مع التطبيق عند تدوير الشاشة أو عند نفاد الذاكرة. أخيراً، توجنا هذه المعرفة في الوحدة السادسة بتعلم كيفية إنشاء نوافذ الحوار (Dialogs) الآمنة ضد تدوير الشاشة، وكيفية عرض القوائم الطويلة بكفاءة عالية جداً باستخدام RecyclerView و Adapters لتجنب استهلاك الذاكرة (Out-of-Memory). في الاختبار، ركزوا على العلاقات المترابطة: كيف يعيش RecyclerView (الوحدة 6) داخل واجهة مصممة بـ XML (الوحدة 4)، وكيف يستمد بياناته عبر الجافا (الوحدة 2)، وكيف يحافظ على حالته عند تدوير الشاشة باحترام دورة الحياة (الوحدة 5). لقد بذلتم جهداً رائعاً حتى الآن، راجعوا هذه الروابط المفاهيمية بهدوء، وتجنبوا الحفظ السطحي، فالفهم العميق هو طريقكم للتفوق. تمنياتي لكم بكل التوفيق والنجاح في اختباركم غداً!

فخ امتحاني M4
الخلط بين dp و sp. تذكر دائماً: dp للأحجام (مثل الأزرار والهوامش)، و sp للخطوط فقط. استخدام dp للخطوط سيمنعها من التكبير للمستخدمين ضعاف البصر.
فخ امتحاني M2
يعتقد الكثيرون أن نظام ART يترجم الكود أثناء تشغيل التطبيق (Runtime). الحقيقة هي أن ART يقوم بتحويل الـ Bytecode إلى لغة آلة **عند تثبيت التطبيق** (Installation)، مما يجعل التشغيل أسرع بكثير.

مفهوم أساسي M6
الـ RecyclerView لا يقوم بإنشاء View لكل عنصر في القائمة. بدلاً من ذلك، يقوم بإنشاء عدد كافٍ فقط لملء الشاشة، ثم يعيد استخدام (Recycle) هذه العروض أثناء التمرير، مما يوفر الذاكرة بشكل هائل.
فخ امتحاني M6

مفهوم أساسي M2
الفصل بين المنطق والتصميم: في أندرويد، نكتب المنطق البرمجي بلغة Java (أو Kotlin) في ملفات `.java`، ونصمم واجهة المستخدم بلغة XML في مجلد `res/layout`. هذا الفصل يسهل صيانة وتطوير التطبيقات.
مفهوم أساسي M4
تصميم واجهة أندرويد حساس للسياق (Context-sensitive). هذا يعني أن خصائص XML المتاحة لعنصر ما تتغير بناءً على التخطيط الأب (مثلاً layout_weight لا يعمل إلا داخل LinearLayout).
مفهوم أساسي M1
الهدف الأساسي من Stack Overflow ليس النقاش، بل إيجاد حلول دقيقة لمشاكل برمجية محددة. الأسئلة العامة تُرفض فوراً.
سر الامتحان M1
تم إنشاء Git في الأصل بواسطة لينوس تورفالدس لسبب محدد جداً: إدارة الكود المصدري الضخم لنواة نظام التشغيل لينكس (Linux Kernel).
مفهوم أساسي M3
الترابط بين Java و XML هو جوهر تطوير أندرويد. ملفات XML تصمم الواجهة، وملفات Java تتحكم في المنطق، ويتم الربط بينهما باستخدام فئة `R` (مثل `R.id.fab`).
فخ امتحاني M1
الخلط بين Git و GitHub. تذكر دائماً: Git هو الأداة (البرنامج) التي تعمل على جهازك، بينما GitHub هو الموقع (الخدمة السحابية) الذي ترفع عليه عملك.
فخ امتحاني M5
الاعتقاد بأن دالة onDestroy تُستدعى دائماً وبشكل فوري عند خروج المستخدم من التطبيق. في الواقع، قد يقتل النظام العملية (Process) دون استدعاء onDestroy إذا كان بحاجة ماسة للذاكرة، لذا يجب حفظ البيانات المهمة في onPause.
فخ امتحاني M2
